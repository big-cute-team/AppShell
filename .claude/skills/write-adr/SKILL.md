# ADR 작성

ADR은 **왜 그렇게 했는지**를 남기는 문서입니다. 코드를 읽으면 알 수 있는 "무엇을"이 아니라,
코드에 남지 않는 "왜"와 "무엇을 포기했는지"를 기록합니다.

## 먼저: 정말 필요한가

아래 중 **하나라도** 해당하면 씁니다.

- 되돌리기 비싼 선택을 했다 (프레임워크, 빌드 파이프라인, 배포 방식, 데이터 모델)
- 두 개 이상의 선택지를 놓고 하나를 골랐다
- 흔히 쓰는 방식을 일부러 따르지 않았다
- 6개월 뒤 누군가 "왜 이렇게 했지?"라고 물을 만하다

해당 없으면 **쓰지 마세요.** 단순 버그 수정, 오타, 리네이밍, 명백한 관용 구현은 ADR 대상이 아닙니다.
내용 없는 ADR이 쌓이면 진짜 중요한 결정이 묻힙니다.

## 절차

### 1. 번호 정하기

```bash
ls docs/adr/
```

가장 큰 번호 + 1. 4자리 0 패딩. 파일명은 `NNNN-kebab-case-제목.md`.

### 2. 작성

[`docs/adr/TEMPLATE.md`](../../../docs/adr/TEMPLATE.md)를 따릅니다. 섹션은 5개입니다.

| 섹션 | 무엇을 쓰나 |
| --- | --- |
| 머리말 | 상태 / 날짜 / 관련 문서·PR 링크 |
| 배경 | 어떤 상황이었는지. **제약을 사실로** — 환경, 버전, 시간, 정책 |
| 결정 | 무엇을 하기로 했는지. 단정적으로 |
| 대안과 트레이드오프 | 표로. **탈락 이유**가 핵심 |
| 결과 | 생긴 제약 / 되돌리는 비용 / 후속 TODO 링크 |

### 3. 좋은 ADR의 조건

- **구체적인 사실을 넣으세요.** "환경이 안 맞았다"가 아니라
  "기본 JDK가 24라 RN Android Gradle 빌드와 어긋났다".
  버전 번호, 명령 출력, 에러 메시지를 그대로 인용하면 6개월 뒤에도 검증 가능합니다.
- **탈락한 대안에 공을 들이세요.** 채택안은 코드를 보면 알지만, 왜 다른 걸 안 했는지는
  이 문서에만 남습니다. 재검토하는 사람이 읽을 유일한 단서입니다.
- **되돌리는 비용을 추정하세요.** "반나절" / "전면 재작성" 정도의 해상도면 충분합니다.
- **실패와 시행착오도 적으세요.** 처음에 A로 했다가 B로 바꿨다면 그 이유가 가장 값진 정보입니다.
- 분량보다 밀도. 읽는 사람이 결정을 재현할 수 있으면 충분합니다.

### 4. 인덱스 갱신

`docs/adr/README.md` 하단 표에 한 줄 추가합니다. 빠뜨리면 아무도 못 찾습니다.

### 5. 후속 작업 연결

ADR이 남긴 숙제가 있으면 `docs/todo/`에 항목을 만들고 서로 링크합니다.

## 하지 말 것

- **이미 `Accepted`인 ADR의 내용을 고쳐 쓰지 마세요.** 결정이 바뀌면 새 ADR을 쓰고,
  기존 ADR의 상태 줄만 `Superseded by ADR-NNNN`으로 바꿉니다.
  ADR의 가치는 "그때 무엇을 알고 있었는가"의 기록에 있습니다.
- 여러 결정을 한 ADR에 뭉치지 마세요. 나중에 하나만 뒤집을 때 곤란해집니다.
- 아직 안 한 일을 ADR에 쓰지 마세요. 그건 `docs/todo/` 담당입니다.
