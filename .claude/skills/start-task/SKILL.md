# 작업 브랜치 만들기

이 저장소는 **main에 직접 커밋하지 않습니다.** 모든 변경은 브랜치 → PR을 거칩니다.
파일을 수정하기 **전에** 이 절차를 끝내세요. 이미 수정을 시작했다면 지금이라도 실행하면 됩니다
(작업 디렉터리 변경은 브랜치를 바꿔도 따라옵니다).

## 1. 현재 상태 확인

```bash
git branch --show-current
git status --short
```

- 이미 `<type>/<slug>` 형태의 작업 브랜치 위에 있고, 그 브랜치가 **이번 작업을 위한 것**이라면
  새로 만들지 말고 그대로 진행하세요.
- `main`, `master`, 또는 `<이름>/main` 같은 개인 기본 브랜치 위에 있다면 반드시 새 브랜치를 만듭니다.

## 2. 브랜치 생성

```bash
git fetch origin
git switch -c <type>/<slug> origin/main
```

`origin/main`을 기준으로 삼습니다. `git switch main`은 쓰지 마세요 —
이 저장소는 worktree로 운영될 수 있어 `main`이 다른 곳에 체크아웃되어 있으면 실패합니다.

### 브랜치 이름 규칙

`<type>/<slug>` — 소문자, 하이픈 구분, 영어.

| type | 쓰임 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `chore` | 설정, 의존성, 빌드 |
| `docs` | 문서만 |
| `refactor` | 동작 변화 없는 구조 개선 |

예: `feat/push-notifications`, `chore/expo-sdk-58`, `fix/android-back-button`

slug는 3~5 단어 이내로 **무엇을 하는지** 드러나게. 이슈 번호가 있으면 뒤에 붙입니다
(`feat/deep-links-42`).

## 3. 작업 중 커밋하지 않기

작업 도중에는 커밋하지 않아도 됩니다. 커밋·푸시·PR은 [`wrap-session`](../wrap-session/SKILL.md) 스킬이
작업 마무리 시점에 한 번에 처리합니다. 다만 되돌리기 어려운 큰 변경 전에는
중간 커밋을 남겨 두면 안전합니다.

## 주의

- 사용자가 명시적으로 "main에 바로 커밋해"라고 하지 않는 한 예외를 만들지 마세요.
- 브랜치를 만들었으면 **사용자에게 브랜치 이름을 알려주세요.** 한 줄이면 됩니다.
- 작업 성격이 도중에 크게 바뀌었다면(예: 버그 수정하러 갔다가 기능을 만들게 됨)
  브랜치 이름을 바꾸는 것보다 그냥 진행하고 PR 제목에서 정확히 설명하는 편이 낫습니다.
